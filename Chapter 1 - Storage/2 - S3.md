## Core Concepts - Answers

1. **Data Model & API:**
- S3 object model:
    - buckets - A bucket is a container for objects.
    - objects - An object is a file and any metadata that describes that file.
    - keys - The name that you assign to an object. You use the object key to retrieve the object.
    - versions - Within a bucket, a key and version ID uniquely identify an object. The version ID is a string that Amazon S3 generates when you add an object to a bucket.
- How it differs from a hierarchical file system?
Flat Storage Structure, where it organize all files at the same level, without directories or subdirectories, akin to placing all documents in a single folder. Relies on metadata tags and unique identifiers to categorize and retrieve files, compensating for the lack of nested directories. When you search for an object in S3 it doesn't search the object in an herarchical way (dive in according the path).Instead, It scans under the prefix which defines as "path" and directories but its actually the key of the S3 object. 
- Typical REST operations - object operations: GET, PUT, DELETE, HEAD. Bucket opreations: CreateBucket, listsBucket, GetBucketPolicy
- Why is the namespace flat rather than directory-based? In directory-based, to find a file, the computer must look at the root folder, then the subfolder, then the next subfolder. In big amount of data, the lookups becomes slower. In addition, in block storage the data breaks into fixed-size chunks and stored them in disk which supply extremly fast latency. Much of the space might remain unused. It doesn’t scale automatically. In contrast to them, you give S3 your data, and S3 gives you a unique Key (the ticket). When you want your data back, you present the Key. Because there is no hierarchy (no “walking down the folder tree”), retrieving the 1st file is just as fast as retrieving the 1 billionth file. This is why S3 can hold petabytes of data without slowing down.

2. **Metadata & Immutability:**
- How is metadata stored and retrieved in S3-compatible systems? When you upload a file to S3, it is stored as an S3 object. Objects consist of the file data and metadata that describes the object.
S3 metadata provides three types of metadata:
    - system-defined metadata - object's creation time and storage class.
    - user-defined metadata - tags and metadata that was included.
    - Event metadata, such as when an object is updated or deleted.
- object immutability - S3 Object Lock implements a Write Once, Read Many (WORM) model. TObject Storage Immutability ensures data integrity by stopping stored objects from being deleted or overwritten during a specific retention timeframe. With Object Storage Immutability (Object Lock) enabled on a container, it is impossible to modify or shorten the retention period for an existing object. Immutability ensures object version integrity and availability throughout the defined retention period. To update data, a new object is created rather than modifying the existing one.
- versioning - S3 Versioning is a feature provided to keep multiple versions of an object in one bucket so that you can restore objects that are accidentally deleted or overwritten. If you enable versioning for the bucket, S3 automatically adds a unique version ID to the object that is stored in the bucket. For example, in one bucket you can have two objects with the same key (object name) but different version IDs, such as photo.gif (version 111111) and photo.gif (version 121212).
- how these features enable durability, auditing, and recovery patterns?
durability can be applied with object immutability when you lock an object and allow only to read from it. recovery patterns can be provide with the versioning feature with rollback to the previous version and replication prevents recovers. Auditing is provide by storing to each object its metadata.

3. **Consistency & Performance:**
- What consistency guarantees do modern object stores provide (eventual vs strong)?
    - Strong consistency - providing read operations which always returns the most recent acknowledged write. A predictable behavior and simple logic for the applications.
    - Eventual consistency - Replicas converge over time, but reads may return stale data. Will required from the application to have functionalities of polling, retries or version tracking.

Minio and Ceph doesnt support eventual consistency,  their'e compatible way allows only strong consistensy implementation. In Amazon S3 there was in the past an eventual consistency and now it also supports the strong one. 

N - replication factor\
W - minimum replicas needed for a write\
R - minimum replicas needed for a read\
Strong consistency is possible when W + R is bigger than N. When it is not, eventual consistency become possible. In the beginning s3 writes and deletes were asynchronously which means eventual consistency but then client has a lot of integrity problems or 404. Therefore, the new design has strong consistency such as an action is acknoledge when its applied in the quorum of the metadata nodes, after that it replicates asynchronously. (but metadata is synchronous).
- How do multipart uploads, parallelism, and range reads affect performance?
    - multipart uploads - Multipart upload allows us to upload a single object as a set of parts. We can upload these object parts independently and in any order. Post completion, S3 combines the smaller pieces into the original larger object. In general, when the object size reaches 100 MB, we should consider using multipart uploads instead of uploading the object in a single operation. It can also recover from a network error more quickly by only restarting the upload for the failed parts. You increase performance by multiple uploads.\
    object visibility -  multipule uploads can be visible only after the client sends to s3 that the upload has copleted and it can assemble the parts, the s3 returns an ack the the object has created and then its reachable.
    - parallelism - S3 provides industry leading performance for cloud object storage. S3 supports parallel requests, which means you can scale your S3 performance by the factor of your compute cluster, without making any customizations to your application. Performance scales per prefix (a string of characters at the beginning of the object key name simulating a folder structure.), so you can use as many prefixes as you need in parallel to achieve the required throughput. There are no limits to the number of prefixes. Also contribute to increase performance.
    - range reads - Parallelize GETs by requesting specific byte ranges. Better resilience in case of failures (retries). Can be used to retrieve partial data (head of a file). Increase performance by getting only the relevent part of the file without download all of the file.
- trade-offs for small vs large objects and listing operations?
Writing small files to object storage is straightforward, but queries over them will run much slower, or even fail to complete. Querying many small files incurs overhead to read metadata, conduct a non-contiguous disk seek, open the file, close the file and repeat. The overhead is only a few milliseconds per file, but when you’re querying thousands, millions or even billions of files, those milliseconds add up. The solution is to write in batches. In contrast writing and reading large files can be very heavy and slow down the operations like load the files and read the file synchronomus. Thats why S3 has features which improves performance such as parallelism, range reads and multiple uploads. At last, listing operation allows S3 keys to be listed with a given prefix. S3 buckets often store large numbers of keys. Even when the keys are distributed within “sub-directories”, the contents of a sub-directory often cannot be listed in a single operation because the number of keys returned would not fit in memory. As buckets can contain a virtually unlimited number of keys, the complete results of a list query can be extremely large. o manage large result sets, the Amazon S3 API supports pagination to split them into multiple responses. Each list keys response returns a page of up to 1,000 keys with an indicator indicating if the response is truncated. You send a series of list keys requests until you have received all the keys.

4. **Durability, Distribution & Scaling Architecture:**
- How do object stores achieve durability at scale using replication or erasure coding? S3 is designed to exceed 99.999999999% data durability.
Erasure coding is a data protection method that breaks data into smaller fragments, expands them with redundant data pieces, and stores them across different locations. This method ensures that the original data can still be reconstructed even if some fragments are lost or corrupted.
    - Involves storing multiple copies of the same data across different locations. While it provides redundancy, it requires significant storage overhead and is less efficient. S3 makes copies of it across different data centers (availability zones) in the same region. This way, even if one data center goes down, your data is still available.
    - Provides higher durability by storing data fragments across many locations. Even if several fragments are lost, the original data can still be recovered. This method significantly reduces the risk of data loss compared to replication.

But it has also disadvantages when using erasure coding - 
    - It increased the number of storage nodes when it comes to breaking the data into smaller piecies.
    - Increased latency. It takes longet to retrieve and repair the fragments.
    - Increase usage of computer resources.
- Explain how data and metadata are distributed across nodes?
    - Data service - Monitor the health of storage nodes (via heartbeats). Distribute writes and reads across nodes. Write and read object data from nodes. Replicate data to ensure fault tolerance.
    - Storage Nodes - Multiple small objects are appended to a single large file. When a file grows large (e.g., 2 GiB), it’s closed and a new one is started. This is why S3 objects are immutable — they’re written once into these logs.
    - S3 metadata service - The metadata service in S3 keeps track of bucket and object information. Storing bucket metadata (used when creating a bucket), Storing object metadata (used when uploading an object), Looking up object metadata by name (used when downloading an object).
- how failures are detected and repaired?
Every object is stored with a checksum (like an MD5 or SHA hash). Runs regular background checks to detect bit rot or silent corruption. If corruption is detected, S3 automatically repairs it using a clean copy from another AZ.
- how systems scale to billions of objects through partitioning and request routing? S3 uses the Domain Name System (DNS) to route requests to facilities that can process them. This system works effectively, but temporary routing errors can occur. If a request arrives at the wrong Amazon S3 location, Amazon S3 responds with a temporary redirect that tells the requester to resend the request to a new endpoint.
Partitions are data organized hierarchically, defining the location where the data for a particular partition resides. Partitioning your data allows you to limit the amount of data scanned by S3 SELECT, thereby improving performance and reducing cost.
5. **Security, Deployment & Ecosystem Integration:** 
- Outline authentication and authorization mechanisms (request signing, IAM policies, ACLs) and how they apply to buckets and objects.
IAM policies are json document that defines permissions. S3 receives a request for an object operation, it converts all the relevant permissions— resource-based permissions (object access control list (ACL), bucket policy, bucket ACL) and IAM user policies—into a set of policies to be evaluated at run time. It then evaluates the resulting set of policies in a series of steps. In each step, it evaluates a subset of policies in three specific contexts—user context, bucket context, and object context.

## Q&A  - Answers
1. s3 endpoint - urls used to access S3 buckets and objects. hostname.
2. lifecycle policy considered storage classes - S3 bucket lifecycle policy is a set of rules that define how Amazon S3 manages objects in your bucket over time. Key components of lifecycly policies:
    - Transition Actions - These actions allow you to move objects from one storage class to another based on age. For example, you could transition frequently accessed objects to S3 Standard and then move them to S3 Glacier for long-term storage after a certain period.
    - Expiration Actions - These actions define when objects should be deleted from the bucket. You can set policies to automatically delete objects after a specified number of days, helping manage storage costs and remove outdated data.
    - When versioning is enabled, S3 keeps multiple versions of an object. Lifecycle policies can manage both current and noncurrent versions, allowing you to specify how long to retain older versions before they are deleted.

In an S3 Lifecycle configuration, you can define rules to transition objects from one storage class to another to save on storage costs.
3. S3 storage classes offer different options to optimize cost and performance base of how frequently data is accessed.
Each storage class has its price per GB stored, and per amount of IOPs performed. Additionally each storage class offers different average latencies.
    - S3 Standard - This is the default storage class. Designed for frequently accessed data and stores data in a minimum of three Availability Zones.
    - S3 Standard-Infrequent Access (IA) - Ideal for infrequently accessed data, Stores data in a minimum of three Availability Zones, but costs per operation.
    - S3 One Zone-Infrequent Access - Stores data in a single Availability Zone. Has a lower storage price than Amazon S3 Standard-IA. But slightly lower durability.
    - s3 Glacier - Archivel Storage. Significantly lower storage costs. Retrieving data from Glacier Instant Retrieval incurs a higher cost per GB compared to S3 Standard. This is because Glacier Instant Retrieval prioritizes keeping data readily available for quick retrieval while archived.
4. The limit of an s3 object is 5TB.
5. pre-signed url - he object owner may share objects with others by creating a presigned URL. A presigned URL uses security credentials to grant time-limited permission to download objects. The URL can be entered in a browser or used by a program to download the object. The credentials used by the presigned URL are those of the AWS user who generated the URL.
5. pass style vs virtual hosted style -
Amazon decided to delay the deprecation of S3 path-style URLs to ensure that customers have the time to transition to virtual hosted-style URLs also to add support in virtual hosted-style URLs for the buckets that have dots in their names. S3 currently supports two different addressing models: path-style (old) and virtual-hosted style (new).
    - In path-style URLs, the s3 bucket name will be in the URL path. "https://s3.amazonaws.com/bucket-name/object_key"
    - n hosted-style URLs, the bucket name will be included on the subdomain so we can have distinct DNS subdomains for the buckets. "https://bucket-name.s3.amazonaws.com/object_key"
